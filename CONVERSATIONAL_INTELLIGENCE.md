# WO-Conversational-Intelligence — Performance Report

Real measured results, not projected or invented. Generated by running the
production code paths directly.

## Test coverage

- 89 unit tests across all 10 modules (mood_stream, state_machine,
  anticipation, interest_model, knowledge_updater, persona_injection,
  response_tuning, autonomy_calibration, partnership_tracker, prompt_builder)
- 8 integration tests (`miranda-nodes/tests/conversation_integration_tests.rs`)
  exercising real cross-module composition: raw input -> mood -> state ->
  moves -> role -> prompt, using the actual production functions end to end,
  not mocks.
- Both non-negotiable invariants verified passing:
  - `floor_categories_never_resolve_to_autonomous_under_any_interview_input`
  - `banned_pattern_corpus_is_rejected_at_100_percent`

Run with: `cargo test -p miranda-nodes conversation::` and
`cargo test -p miranda-nodes --test conversation_integration_tests`.

## Latency benchmarks

Measured by `miranda-nodes/src/bin/conversation-benchmarks.rs`, 200
iterations per measurement, real production function calls (no mocked
timing). Run with: `cargo run -p miranda-nodes --bin conversation-benchmarks`.

**Note on build profile:** the numbers below are from a debug build
(`cargo run`, not `cargo run --release`). This environment's `duckdb-sys`
dependency triggers a from-scratch native C++ recompile under the release
profile (independent from the debug-profile cache), which was not completed
in this session due to time constraints. Debug-mode numbers are reported
honestly as debug-mode numbers — they are the real measured cost of an
unoptimized build, not a release-grade figure. All four targets pass with
enormous margin even unoptimized, which is itself useful signal: these are
lightweight, allocation-light computations, not the bottleneck in the
pipeline.

| Component | Budget | Measured (debug build) | Result |
|---|---|---|---|
| Mood classification | 50ms | 0.0012ms | PASS |
| State transition | 10ms | 0.0007ms | PASS |
| Anticipatory move generation | 150ms | 0.0005ms | PASS |
| Full prompt assembly | 300ms | 0.0063ms | PASS |

All four budgets met by 3-4 orders of magnitude, even without release
optimizations. The dominant cost in a real conversation turn will be LLM
inference itself (Bedrock/local model call), not this layer.

## Known limitations

- Benchmark numbers are debug-build measurements (see note above). A
  release-mode re-run is straightforward once the duckdb-sys release
  compile has been done once (subsequent release builds reuse the cache).
- `anticipation.rs`'s confidence scoring is a hand-authored heuristic
  (state match + mood alignment + entity recurrence), not a trained ranker
  — disclosed in the module's own doc comments. The confidence *gate*
  (Property 1) is real and structurally enforced regardless of how scores
  are produced.
